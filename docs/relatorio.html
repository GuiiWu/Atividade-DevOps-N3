1. Visão geral

Desenvolvi uma API "Loja" em Node.js (Express) que guarda produtos no MySQL e usa o Redis como cache da lista de produtos e contador de visitas compartilhado entre as réplicas. Toda a configuração vem de variáveis de ambiente. Por isso a mesma imagem roda com docker run, no Compose (.env) e no Kubernetes (ConfigMap + Secret). A API tem duas rotas de saúde: /health (liveness: o processo está vivo) e /ready (readiness: banco e Redis respondem). Todas as respostas trazem a versão e o nome do pod que atendeu, o que deixa visíveis o balanceamento, o rolling update e o canary.

6.6 Nó: Capacity, Allocatable e Allocated resources

Capacity é o total de recursos físicos que o nó informa ter: aqui 12 CPUs e 8104720Ki (~7,7 GiB) de memória, que é o que o WSL 2 entrega para a VM do Docker Desktop, e no máximo 110 pods. Allocatable é quanto desse total o scheduler pode realmente distribuir para pods, ou seja, a capacidade menos o que fica reservado para o sistema operacional, o kubelet e o limite de despejo (eviction). Aqui sobram 8002320Ki de memória: ~100 MiB ficaram reservados. Allocated resources é a soma das requests e limits de todos os pods que estão no nó, em relação ao Allocatable. No momento do print, as requests somavam 1450m de CPU (12%) e 1272Mi de memória (16%). O scheduler só coloca um pod novo se a request dele couber no que falta (Allocatable − requests alocadas). Os limits podem passar de 100% (overcommit), como o próprio describe avisa, porque nem todo pod usa o limite ao mesmo tempo.

7. Bônus

7.1 Build multi-stage

O Dockerfile tem dois estágios. O deps roda npm ci --omit=dev, e o runtime parte de outra node:22-alpine limpa e copia só a pasta node_modules pronta e o código. Cache do npm, manifestos intermediários e ferramentas de build não chegam à imagem final, que ficou com 63,3 MB (tamanho do conteúdo).

7.2 Canary

No canary, a versão nova vai primeiro para uma parte pequena dos usuários. Se der problema, só essa fatia é afetada, e voltar atrás é só apagar o canary. Implementei com um segundo Deployment, loja-api-canary (k8s-extras/canary.yaml), com a imagem 3.0, 1 réplica e os labels app: loja-api, track: canary. 8. Respostas

1. Qual a diferença entre imagem e container? O que faz cada instrução do seu Dockerfile?

A imagem é o pacote pronto e somente-leitura: sistema base, Node, dependências, meu código e as instruções de como iniciar. É como uma "receita congelada", identificada por nome e tag (loja-api:1.0). O container é uma imagem em execução: um processo isolado com uma camada gravável por cima da imagem, rede e nome próprios. Da mesma imagem eu criei vários containers ao mesmo tempo (no Compose e nos pods do Kubernetes). Apagar o container não apaga a imagem.

FROM node:22-alpine AS depsPrimeiro estágio, só para instalar dependências. Alpine é a variante enxuta do Node (~50 MB).
WORKDIR /appCria e entra na pasta /app. Os comandos seguintes rodam nela.
COPY package.json package-lock.json ./Copia só os manifestos primeiro. Se eu mudar o código e não as dependências, o Docker reaproveita o cache da camada do npm ci.

2. O Compose usa depends_on e healthcheck. Como o Kubernetes resolve o problema de "esperar o banco ficar pronto"?

O Kubernetes não tem depends_on: ele sobe tudo ao mesmo tempo e trabalha com reconciliação, ou seja, fica tentando até o estado real ficar igual ao desejado. Quem espera o banco são as próprias peças:

  • readinessProbe: minha API só é considerada "pronta" quando /ready devolve 200, o que só acontece quando MySQL e Redis respondem. Enquanto não está pronta, o Service não manda tráfego para ela. Isso aparece nos eventos como Readiness probe failed: … 503 logo no início.
  • initContainer: coloquei o espera-mysql (busybox com nc -z mysql 3306 em loop). O container da API nem inicia antes de a porta do banco abrir. O log mostrou "aguardando mysql..." três vezes e depois "mysql respondeu".
  • Reinício automático: se a API morrer por falta do banco, o kubelet reinicia o container com espera crescente (CrashLoopBackOff), até dar certo.
  • A aplicação é tolerante: o db.js tenta conectar 30 vezes com 2 s de intervalo, e o Redis reconecta sozinho.

No MySQL também usei readinessProbe (mysqladmin ping com o usuário da aplicação), então o Service mysql só aponta para o pod quando ele já aceita login.

3. O que são requests e limits? Justifique os valores que você escolheu.

Request é quanto de CPU e memória o container tem garantido. O scheduler usa esse valor para escolher um nó com espaço e reserva o recurso. Também é a base do percentual do HPA. Limit é o teto: se a CPU passar do limit, o container é estrangulado (throttling, fica mais lento); se a memória passar do limit, o container é morto (OOMKilled). Com request menor que limit o pod fica na classe QoS Burstable.

API100m / 128Mi400m / 256MiParada, ela usa 1–10m de CPU e ~22–25Mi de RAM. 100m de request é pouco para o nó e dá ao HPA uma base clara: 50% = 50m por pod. O limit de 400m deixa a API absorver picos sem tomar o nó todo: no início da carga, com 2 pods, a média chegou a ~311m por pod, abaixo do teto. 128Mi/256Mi dão folga de 5–10x para o heap do Node e os buffers do Express. Comecei com 96Mi/192Mi no YAML e aumentei com kubectl set resources na Parte 4.

4. Explique Deployment, ReplicaSet e Service. Como o Service encontra os pods?

O Deployment é onde eu declaro o estado desejado da aplicação: qual imagem, quantas réplicas e como atualizar. Ele não cria pods diretamente: cria um ReplicaSet para cada versão do template. O ReplicaSet tem um único trabalho, que é manter N pods iguais rodando, recriando qualquer um que morra (foi o que aconteceu quando apaguei o pod do MySQL). No rolling update o Deployment cria um ReplicaSet novo (ex.: loja-api-5fbd9554c para a 2.0) e vai aumentando ele enquanto diminui o antigo. Os ReplicaSets antigos ficam com 0 réplicas e são o que permite o rollout undo.

O Service dá um endereço fixo (IP virtual + nome DNS loja-api) para um conjunto de pods que nascem e morrem com IPs diferentes, e balanceia o tráfego entre eles. Ele encontra os pods por labels: o selector do Service (app: loja-api) é comparado com os labels de todos os pods do namespace. Os pods que batem e estão Ready entram nos EndpointSlices (no print: 10.1.0.9,10.1.0.10), e o kube-proxy direciona o tráfego para esses IPs. Por isso, no canary, bastou criar pods com o mesmo app: loja-api para eles começarem a receber parte das requisições.

5. Por que base64 não é segurança? Onde deveriam ficar senhas de verdade em produção?

Base64 é só uma codificação, não uma criptografia: não tem chave e qualquer um reverte. dHJvcXVlLWxvamEtMTIz, do meu Secret, vira troque-loja-123 com um comando ([Text.Encoding]::UTF8.GetString([Convert]::FromBase64String("...")) ou base64 -d). Ele existe para guardar bytes arbitrários em YAML/JSON. Quem tem acesso ao arquivo no Git, ou permissão de kubectl get secret -o yaml, tem a senha. Por isso no repositório só há senhas de exemplo de laboratório.

Em produção as senhas deveriam ficar num cofre de segredos: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault ou GCP Secret Manager, sincronizados com o cluster pelo External Secrets Operator ou pelo Secrets Store CSI Driver. Outra opção é Sealed Secrets, em que o Git guarda o segredo criptografado com uma chave que só o cluster tem. No cluster, também é preciso ativar a criptografia do etcd em repouso, restringir via RBAC quem pode ler Secrets e trocar as senhas periodicamente. Nunca senha em texto ou base64 dentro do repositório.

6. Explique o seu HPA: o que são mínimo, máximo e o percentual de CPU, e o que aconteceu no seu teste.

O HorizontalPodAutoscaler ajusta sozinho o número de réplicas do Deployment conforme uma métrica. Criei com kubectl autoscale deployment loja-api --min=2 --max=6 --cpu=50%:

  • Mínimo (2): nunca fica com menos de 2 pods, mesmo sem uso. Assim continua havendo redundância se um pod cair.
  • Máximo (6): teto para a escala não consumir o nó inteiro (nem a conta da nuvem, num caso real).
  • 50% de CPU: é a média de uso em relação à request de CPU dos pods. Com request de 100m, o alvo é 50m por pod. A cada 15 s o HPA calcula réplicas desejadas = réplicas atuais × (uso atual ÷ alvo), arredondando para cima. Por isso o HPA só funciona com requests definidas e com o metrics-server instalado.

O que aconteceu no meu teste (seção 5.4):

  1. Antes (10:32–10:34): 1% de CPU e 2 réplicas. No começo apareceu <unknown> até o metrics-server coletar a primeira amostra.
  2. Durante: às 10:34:09 liguei o gerador-carga (3 pods busybox fazendo wget em loop em http://loja-api/carga?ms=50, ou seja, pelo DNS interno do Service). A média foi a 311%. A conta deu 2 × 311/50 ≈ 12,4 réplicas, mas o máximo é 6, então o HPA escalou direto para 6. O describe hpa mostra New size: 6; reason: cpu … above target e a condição ScalingLimited … TooManyReplicas. Com 6 pods cada um ficou com ~170–270m (kubectl top pods), e a média ficou em ~210%, ainda acima de 50%. A escala ficou presa no máximo, o que mostra que para essa carga 6 réplicas ainda seriam poucas.
  3. Depois: às 10:38:11 apaguei o gerador. Quando a métrica atualizou, o uso caiu para 1–2%. Depois da janela de estabilização (reduzi de 300 s para 60 s com o patch hpa-behavior-patch.json, só para a demonstração), o HPA voltou para 2 réplicas (o mínimo): New size: 2; reason: All metrics below target.

Notei também que a subida é rápida e a descida é lenta de propósito: a janela de estabilização evita que o número de pods fique "pulando" quando a carga oscila.

7. Quando o rollout undo é útil? Relate a falha proposital que você fez e como a diagnosticou.

O rollout undo serve para voltar rápido para a última versão que funcionava quando uma atualização dá errado: imagem inexistente, bug que derruba a aplicação, configuração errada, probes falhando. Ele não precisa de build nem de alterar YAML: o Deployment reativa o ReplicaSet anterior, que ainda está guardado (revisionHistoryLimit: 10). Também dá para escolher a revisão com --to-revision=N.

Minha falha: com a API na 2.0, rodei kubectl set image deployment/loja-api api=loja-api:9.9-nao-existe. O rollout status não terminou (timed out waiting for the condition), e o get pods mostrou um pod novo 0/1 ImagePullBackOff ao lado dos 2 pods antigos ainda Running. No kubectl describe pod fui direto na seção Events, que mostrou Pulling image "loja-api:9.9-nao-existe" → Failed to pull image … pull access denied for loja-api, repository does not exist → ErrImagePull → Back-off pulling image. Ou seja, a tag não existe localmente nem no Docker Hub. O kubectl get events --field-selector type=Warning confirmou. Graças ao maxUnavailable: 0 o usuário não percebeu nada: /health continuou respondendo versao 2.0. Rodei kubectl rollout undo deployment/loja-api, o pod quebrado foi removido, e o histórico mostrou a revisão 2 (a 2.0) reaparecendo como revisão 4.

8. Que limitações a sua solução tem? O que você melhoraria para produção?

  • Banco com uma réplica só: o MySQL é um Deployment com 1 pod e estratégia Recreate. Se o pod cair, o banco fica fora até o novo subir (~15 s no teste). Não dá para escalar para várias réplicas, porque todas escreveriam no mesmo volume e corromperiam os dados. Para produção eu usaria um banco gerenciado (RDS, Cloud SQL) ou um StatefulSet com operador (MySQL Operator, Percona) com replicação primário/réplica.
  • Volume local: o PVC usa o hostpath do Docker Desktop, ou seja, o disco de um único nó. Se o nó morrer, os dados vão junto. Precisaria de storage de rede (EBS, Azure Disk) e backups automáticos com teste de restauração.
  • Segredos no Git: mesmo de exemplo, o Secret está no repositório. Em produção: Vault, External Secrets ou Sealed Secrets (ver resposta 5).
  • Imagens só locais: o cluster usa as imagens do Docker da máquina (imagePullPolicy: IfNotPresent). Em produção eu publicaria num registry (Docker Hub, GHCR, ECR) com tags imutáveis e um pipeline de CI/CD (GitHub Actions) para testar, construir, escanear vulnerabilidades e fazer deploy.
  • Cluster de um nó: todas as réplicas ficam na mesma máquina, então réplicas não protegem contra falha do nó. Precisaria de vários nós, podAntiAffinity/topologySpreadConstraints e um PodDisruptionBudget.
  • Exposição: NodePort sem HTTPS. O caminho é o Ingress (bônus) com TLS via cert-manager, mais NetworkPolicies para que só a API fale com o MySQL e o Redis.
  • Redis sem persistência no Kubernetes (no Compose tem AOF): como é cache, aceitei perder o contador de visitas. Para dado importante, usaria um volume ou Redis gerenciado.
  • Observabilidade: só tenho kubectl logs e top. Adicionaria Prometheus + Grafana, logs centralizados e alertas. O HPA também poderia escalar por requisições por segundo, e não só por CPU.
  • Governança do namespace: ResourceQuota e LimitRange para impedir que alguém crie pods sem requests e limits.

9. Conclusão

A mesma imagem passou pelos três ambientes (docker run, Compose e Kubernetes), mudando só a forma de injetar a configuração. O que mais aprendi foi a diferença entre "o container iniciou" e "o serviço está pronto", que no Compose se resolve com healthcheck + depends_on e no Kubernetes com readiness/liveness, initContainer e a reconciliação contínua. Também vi na prática como o Deployment protege a disponibilidade: atualização sem nenhum erro, imagem quebrada sem afetar o usuário e volta com um comando.
